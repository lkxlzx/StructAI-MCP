## 三、本轮的裁决（**不要重新争论**）

这些都是**实测得出**的，重开话题前请先读证据。

### 3.1 路由方向：实例 → 适配器 → 能力（总纲 §4.9.1）

**反向是数据损坏路径。** 实测：三产品都注册时，不带 `adapter` 的调用**成功返回 Gen 的数据**，
调用方以为在操作 Civil。所以 `>1` 且未指定 **必须拒绝**（`VALIDATION_ERROR`），不许猜。

### 3.2 `product_scope='unknown'` 乐观放行（总纲 §4.2.11）

手册的产品标注**不可信**：声明「Civil 专属」的 47 个端点里，**32 个在 Gen NX 上同样应答**。
在探测完成前藏起一大片能力，比带着 `unverified` 警告放行更糟。

### 3.3 手册的「中文段」里没有中文

Gen 的 `## JSON数据手册` 条目标题是英文（`#### Main Control Data`），`__DESC__` 也是英文。
**对 API 而言中英文段是同一批端点的两次记录**——已按此合并去重（索引表内合并 1,152 次）。

### 3.4 抽取的 `request_schema_json` **不是** MCP payload schema

604 个里 594 个是**手册的请求示例**。把它当 schema 会让每个不等于该示例的调用都被拒。
因此播种器**不写该列**（保持 NULL），值留在 `metadata_json.extraction_request_schema`。
**后果：播种行在 `request_schema` 上比静态声明宽松，这是有意的。**

### 3.5 `capabilities.constraints_json` 是能力级扩展容器（总纲 §4.2.13）

`dispatch` / `adapter_action` / `task_type` / `notes` **没有对应列**，走这里。
**每能力专属的值绝不能放 `metadata_json`**——`tool_interfaces` 一行可被多个能力共享。

### 3.6 云端中继是**转发**的（对接规范 §11.5.16）

注册的 MIDAS 实例下线后，中继对**一切路径**返回 `404 client does not exist`。
这是**应用层失败，不是传输层**——重试无用。我们的会话诊断已正确报出 `service_down`。

## 四、下一步做什么

### 4.0 ⚠️ 最要紧的一步：平台从未被引导过

**这是"续接"的真正断点。** 上面那张表说明：参考数据在，但**没有任何用户、没有任何 MIDAS 实例**。

**实测的准确情况**（比"代码不存在"更精确）：

| 路径 | 现状 |
|---|---|
| `config/midas.json` → **内存适配器表** | ✅ **通的**。`app/mcp/server.py::register_adapters_from_config` 读配置，逐个 `MidasNxAdapter(connection)` 注册进 `AdapterRegistry`。MCP 今天就是这样跑的 |
| `config/midas.json` → **`midas_clients` 表** | ❌ **不通**。`MidasConnection.to_registry_row()` 写着"Shape this connection for insertion into `midas_clients`"，但**全仓没有任何调用点**（只在文档字符串里被提及）——它是**为数据库声明却从未接线的死代码** |
| 超级管理员 `users` 行 | ❌ 不存在 |

**后果**：`midas_clients` 是空的，而**闸 1（选实例）与数据范围过滤都建立在它之上**。
今天能跑通，只是因为调用方直接给 `adapter` 参数绕过了选实例——**那正是闸 1 要禁止的路径**。

**要做的**：

1. 一个引导入口：读 `config/midas.json` → 写 `midas_clients`（3 行）+ `adapters`（3 行）
   + 一个超级管理员 `users` 行。**幂等**，重复跑不产生重复行。
   复用 `to_registry_row()`（它已经写好了，只是没人调用）。
2. 让 `create_schema()` 之后自动调用它，或提供一个显式的 `init` 命令。

**验收**：`SELECT COUNT(*) FROM midas_clients` = 3，
且通过 REST/MCP 以超级管理员身份能**按 `client_id`** 列出并调用这三个实例
（即走完闸 1 的正常路径，而不是绕过它）。

> **为什么它排第一**：其余所有工作（闸 4 实机、阶段 6 收敛、前端能力表）
> **都假设平台已经能连上实例**。现在这条链只在**测试夹具**里跑通过，
> **在真实进程里从未跑通过**——真实进程走的是内存注册表那条捷径。

### 4.1 立即可做（互不依赖，可并行）

| # | 事项 | 为什么 | 起点 |
|---|---|---|---|
| **A** | **处置陈旧产物** | `docs/api-registry/` 里有**第二份矛盾注册表**：`midas_api_registry.json`（505 端点，`merge_registry.py` 产物）+ `part-01..16.json` + `ENDPOINT_INDEX.md`。字段名与新的 `interfaces.json` 完全不同，**既不是超集也不是子集** | 决定归档还是删除 |
| **B** | **中文段 `Input Data Form`** | 415 个 claim 拿不到 schema，卡在 **4 空格缩进的围栏**（`_FENCE_RE` 只认 ≤3 空格）。**注意**：权威 draft-07 schema 已从英文段找回（`json_schema` 源 10 → 1037），所以这项**优先级不高** | `extract_interfaces.py` 的 `_FENCE_RE` 与 claim span 逻辑 |
| **C** | **前端能力表 API** | 让前端按 `domain`/`feature` 构建菜单 | `midas_query target=capabilities` 已支持过滤 |

### 4.2 阶段 6：实机收敛 `product_scope`

**这是唯一真正剩下的"阶段"。** 现在 2,517 行的 `product_scope` 全是 `unknown`。

做法：对每个端点，在真实实例上探测它是否存在，把结果写回 `product_scope`。
**必须先想清楚代价**：2,517 行 × 3 产品的探测是**大量实机写/读**，
而 MIDAS 每实例并发恒为 1（对接规范 §2.5.2）。

**建议先做小样本**（比如 `/db/*` 的 200 个端点）验证收益，再决定是否全量。

### 4.3 三条不可违反的顺序约束

1. **改 `interfaces.json` 的产出，必须在灌库验证之后**——否则播种器读到的输入会变。
2. **改 schema 必须在有数据之前**——`tools`/`tool_interfaces`/`capabilities` 目前仍是 **0 行**，
   `create_all` 与 `sql/*.sql` 两条路径都还没被真实数据压过。
3. **规范不能落后于代码**——本轮改了核心路径，规范同步是同一批提交的一部分。

## 五、已知的坑（都踩过）

| 坑 | 表现 | 防范 |
|---|---|---|
| **静默零** | `index_rows=0` 且 `anomalies=0`；2 个 schema 对 619 个标记 | **任何计数都必须有独立判据**。已加自校验：索引行非零、有标记的段必须有 claim、注释覆盖率 <50% 大声失败 |
| **`list` 遮蔽** | `TypeError: 'function' object is not subscriptable` | 类体注解里用 `typing.List`。**本项目已踩两次** |
| **测试全绿但功能是坏的** | `requested_by` 从未写入；civil 部署全线 `ADAPTER_NOT_FOUND` | 断言**行为**（记录的 URL、写库的值），不要只断言信封 |
| **子代理无法执行** | 它们的"通过"都是**预期值** | **一切都要父会话跑**。本轮两个测试失败、一个索引解析 bug、一个缺失词表键，都是**跑出来**才发现的 |
| **编码事故** | 子代理用 `Set-Content` 被重编码成 GBK | 写文件用 `write` 工具；用 `[System.IO.File]::ReadAllText` 验，别用 `Get-Content` 下结论 |
| **`git show :path` 应用了检出过滤器** | 误判工作区是 CRLF | 直接读工作区文件 |
