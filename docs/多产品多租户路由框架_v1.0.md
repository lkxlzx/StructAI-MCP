# 多产品 · 多租户路由框架 v1.0

> 目标：**MCP 同时连接不同用户的不同产品，且任何一次调用都不可能落到错误的实例上。**
> 背景：操作错误的软件会造成数据混乱，因此「不混乱」是硬约束，不是体验优化。

---

## 一、问题本质：路由方向反了

### 现状（错）

```
调用方 → 能力 → capability.adapter_code（硬编码 'midas_gen'）→ 实例
              ↑
        能力决定用哪个实例
```

能力是**全局的、产品无关的**，却被硬编码绑到一个产品上。实测后果：

| 场景 | 今天的结果 |
|---|---|
| 只部署 Civil NX | 每个能力 `ADAPTER_NOT_FOUND`（去找 `midas_gen`） |
| 只部署 Civil Designer | 同上 |
| 三个产品都注册，不指定 | **`success=True`，但静默走了 Gen** |
| 三个产品都注册，`adapter=midas_civil` | `CAPABILITY_NOT_SUPPORTED` |

**第二行和第三行是数据混乱的来源**：用户以为在操作 Civil，实际改了 Gen。

### 目标（对）

```
调用方 → 目标实例(midas_client_id) → midas_clients.adapter_code → 该适配器下的能力
              ↑
        实例决定适配器，适配器决定有哪些能力
```

**`midas_clients.adapter_code` 这一列已经存在** —— 实例→适配器的连接本就在库里，只是从未被用于路由。

---

## 二、目标链路（七步）

```
① 认证       principal = 已验证的身份（user_id / roles / department）
                │
② 数据范围    principal 能用哪些 midas_clients？
              （owner_id / visibility / department，对接规范 §2.5.4 item 5）
                │  → usable: list[MidasClient]
                │
③ 选实例      client_id 指定了吗？  ← **防混乱的核心**
                │  → target: MidasClient
                │
④ 定适配器    target.adapter_code
                │  → adapter_code: str
                │
⑤ 能力可用    (adapter_code, capability_code) 在能力表中？
                │  → 不在 → CAPABILITY_NOT_SUPPORTED
                │
⑥ 产品范围    capability.product_scope 允许该产品？
                │  → 不允许 → CAPABILITY_NOT_SUPPORTED
                │
⑦ 权限       总纲 §4.8.2 的权限码
                │
                └─→ 执行；midas_client_id 贯穿任务与审计
```

**关键差别**：能力解析（⑤⑥⑦）发生在**实例确定之后**，因此永远是「这个实例支持不支持这个能力」，而不是「这个能力绑在哪个实例上」。

---

## 三、防混乱的四道闸

### 闸 1：歧义即拒绝（本次新增，最要紧）

| 可用实例数 | 调用方指定 `client_id` | 行为 |
|---|---|---|
| **0** | — | `CLIENT_NOT_CONNECTED`（没有可用实例） |
| **1** | 否 | **自动选中**（唯一，无歧义） |
| **1** | 是，但不匹配 | `PERMISSION_DENIED`（超出数据范围） |
| **>1** | **否** | **`VALIDATION_ERROR`：必须显式指定 `client_id`** |
| **>1** | 是 | 校验在 `usable` 内 → 用它 |

> **裁决：`>1` 且未指定时必须拒绝，绝不猜测。**
> 今天的实现会「用能力的默认 adapter」，那正是静默走错产品的来源。
> 宁可让调用方多传一个参数，也不能让它改错模型。

### 闸 2：数据范围（已建成）

`scope_allows` + `task_visible_to` 的同一套模式，用户只能使用自己部门/自己的实例。
**它先于选实例执行**，所以「指定了别人的 client_id」表现为 `PERMISSION_DENIED`，而不是越权。

### 闸 3：能力可用性（本次新增）

能力表按 `(adapter_code, code)` 键控。某适配器下没有该能力 → `CAPABILITY_NOT_SUPPORTED`。
**这取代了今天那条方向相反的守卫**（`capability.adapter_code != adapter_code` → 拒绝）。

### 闸 4：产品范围（阶段 0 已建 schema，待接线）

`capability.product_scope` 过滤；`unknown` 乐观放行 + `unverified` 警告。

### 审计（第五道，事后可追）

每次调用记录 `request_id → task_id → adapter_request_id` 之外，新增
**`midas_client_id` + `adapter_code` + `capability_code`** 三元组，
使「这次调用到底落在哪个实例上」事后可查。

## 四、四项改造

### 改造 1：能力表键控（`app/mcp/capabilities.py`）

```python
# 现在：code -> Capability        （同码只能存一行）
_TABLE: dict[str, Capability]

# 改为：(adapter_code or "", code) -> Capability
_TABLE: dict[tuple[str, str], Capability]
```

`adapter_code` 为 `None`（platform-owned）时用空串占位，与 SQL 里 `NULL` 的那一半对应。

公开 API 相应调整：

| 现在 | 改为 |
|---|---|
| `capability_table() -> dict[str, Capability]` | `capability_table(adapter_code=None) -> dict[str, Capability]`（`None` = 全部，键为 `"adapter:code"`） |
| `resolve(tool, action, resource)` | `resolve(tool, action, resource, *, adapter_code)` |
| `register_capability(cap, replace=)` | 键取 `(cap.adapter_code or "", cap.code)` |

**生产代码只有 1 个调用点**（`capability.py:155` 的 `capabilities_of`），
其余约 10 处在测试里，均为机械更新。

### 改造 2：实例选择器（新模块 `app/mcp/routing.py`）

```python
async def select_instance(
    principal, arguments, *, auth_service
) -> MidasClientRef:
    """按 §三 的 0/1/N 规则选出唯一目标实例，或抛出明确错误。"""
```

**这是「不混乱」的唯一实现点**，必须：
- 先做数据范围过滤
- 严格实现 0/1/N 三态
- **不做任何默认回退**

### 改造 3：解析器改为实例驱动（`app/mcp/capability.py`）

```python
# 现在：resolve(tool, action, resource) → 读 capability.adapter_code
# 改为：先由改造 2 得到 adapter_code，再 resolve(..., adapter_code=adapter_code)
```

删掉那条方向相反的守卫（`adapter_code != capability.adapter_code`），
替换为「该 adapter 下有没有这个能力」。

### 改造 4：产品范围过滤接线

在改造 3 的能力解析之后、执行之前，按 `product_scope` 过滤。

## 五、执行步骤（每步可独立验证）

| 步 | 内容 | 验收 | 风险 |
|---|---|---|---|
| **1** | `_TABLE` 键控 + `resolve` 带 adapter | 421 测试更新后全过；`node.list` 在三个 adapter 下各一行 | 中（核心路径，但调用点少） |
| **2** | 实例选择器（0/1/N） | 三态各有测试；`>1` 未指定**必须拒绝** | 低（新模块） |
| **3** | 解析器改为实例驱动 | Civil/Designer 单独部署可用（**今天失败**） | 中 |
| **4** | 产品范围过滤 | `product_scope` 生效；`unknown` 带警告放行 | 低 |
| **5** | 审计三元组 | 每次调用可追到实例 | 低 |
| **6** | 三产品端到端 | 见 §六 矩阵全绿 | — |

**步骤 1 是唯一有实质风险的**（动核心路径）。但影响面已实测：生产代码 1 处。

## 六、验证矩阵（用真实三产品连接）

| # | 场景 | 期望 | 今天 |
|---|---|---|---|
| 1 | 只 Gen，无 `client_id` | 走 Gen | ✓ |
| 2 | 只 Civil，无 `client_id` | **走 Civil** | ✗ `ADAPTER_NOT_FOUND` |
| 3 | 只 Designer，无 `client_id` | **走 Designer** | ✗ `ADAPTER_NOT_FOUND` |
| 4 | 三个都注册，无 `client_id` | **拒绝（歧义）** | ✗ **静默走 Gen** |
| 5 | 三个都注册，`client_id`=Civil 实例 | **走 Civil** | ✗ `CAPABILITY_NOT_SUPPORTED` |
| 6 | 用户 A 指定 B 部门的实例 | `PERMISSION_DENIED` | 部分（数据范围已建） |
| 7 | 对 Civil 实例调 Gen 专属能力 | `CAPABILITY_NOT_SUPPORTED` | ✗ 方向相反 |
| 8 | 同一能力在三个 adapter 各存一行 | 表可容纳 | ✗ 会覆盖 |

**场景 4 和 5 是数据混乱的直接来源，必须由本框架消除。**
